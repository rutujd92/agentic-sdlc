# Scenarios

Each folder holds `scenario.json` (the change request) and `responses/` (recorded agent outputs, replayed by default). Run from the repository root:

```bash
dotnet run --project src/Orchestrator.Cli -- run --scenario scenarios/<name>
```

| Scenario | Request | Demonstrates | Human steps |
|---|---|---|---|
| `smoke` | `GET /api/version` | the full pipeline in about 20 s | approve `merge` |
| `greenfield` | QR code endpoint | parallel agents; tests agent writes outside its lane → retried with feedback; new dependency (QRCoder, MIT) → output review | approve `implement`, approve `merge` |
| `brownfield` | click analytics | cross-layer change; design re-plans a `migration` node (generated by `dotnet ef`); two approvals; reject → rollback | approve `migration` twice, approve `merge` (or `reject … migration`) |
| `ambiguous` | "Make the links safer." | open questions pause the run; clarification re-runs requirements and the pipeline; optional stop/resume | `revise … requirements --guidance "$(cat scenarios/ambiguous/GUIDANCE.txt)"`, approve `merge` |

## How the recordings were made

No API credit was available, so the responses are **hand-authored**. To keep them honest, each scenario's code change was first applied in a scratch worktree and verified with a full build and test run; the responses contain that verified code. The run itself then applies it, builds and tests it again inside the orchestrator's worktree.

Recordings are keyed by node and a hash of the feedback or guidance the node received (`<node>.json`, `<node>.<hash8>.json`). A retry with feedback (greenfield `tests`) or a human clarification (ambiguous `requirements`) therefore replays its own response. The ambiguous scenario's guidance must match `GUIDANCE.txt` exactly; any other answer has no recording and the replay says how to record one.

To replace them with real model output: `--live --record` (needs `ANTHROPIC_API_KEY`).
